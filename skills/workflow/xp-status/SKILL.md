# XP · 大白话进度

把当前任务状态讲给用户听懂。由当前主模型执行；默认中文，除非用户要求详细说明，控制在约 150–300 个汉字，必要时为了准确性适当延长。

## 抓住当前主线

- 从当前可见对话判断用户要完成什么、最新要求、实际结果及未完成项。最新消息通常是在补充原任务，不能只复述最后一句话而丢掉主线。
- 多个任务并存时，先讲当前活跃任务，再用一句话交代相关旧任务的状态；不按聊天顺序逐条回放。
- 区分任务总目标、眼前正在做的步骤和可选建议。不能把“以后可以做”列成已答应但没完成的工作。
- 前序工作已经做完时明确说“这部分已做完，目前没有新的待办”，不为了凑下一步编造任务。不把本轮正在创建/检查进度技能这件事吞掉，也不让它掩盖用户的长期目标。

## 用用户听得懂的话说

默认按以下顺序组织，短段落或几个平行要点均可，不必机械套标题：

1. **我们在做什么**：一句话讲目标，以及它能帮用户解决什么。
2. **现在做到哪了**：已经完成的关键结果和当前阶段，少报文件名、命令、提交编号。
3. **还差什么/卡在哪**：真正未完成的部分、影响及所需条件；没有阻塞就直接说明。
4. **下一步是什么**：已有计划中的实际下一步；如果只是建议，明确说“可以考虑”，不要说成必须执行。

尽量把术语翻成具体动作，例如“已经传到 GitHub”“小样本测试过了”“还没连上真正的调试器”。保留用户需要识别的技能名、模型名或工具名，第一次出现时简短解释，不把关键差异抹平。

不要输出长目录树、技术清单、整段代码、流水账或无关过程。用户问技术细节、指定范围或要求详细说明时，以该要求为准。不要使用拍脑袋的百分比、剩余时间或“基本完成”等模糊说法；直接说明哪一部分做完、哪一部分没验证。

## 准确性边界

- “打算做”“已经写好”“测试通过”“连接真实目标验证过”“已经上传”是不同状态，必须根据现有证据区分。
- 保留会影响用户判断的不确定项和失败。例如离线测试通过但 MCP 连不上，要说“离线测试没问题，连接真实程序这一步还没验证”，不能概括成“全部正常”。
- 当前可见信息不够时，直接说哪一段状态无法确认；没有可靠记忆时不补造。历史交接与旧报告只代表生成时的状态，新消息和实际新结果优先。
- 默认从当前上下文总结，不为简单播报扫描硬盘、翻大量历史、重新测试或连接目标。用户明确要求核实、或有直接影响结论的矛盾时，才做必要的只读检查；保留证据来源，但不向用户倾倒原始日志。
- 不复制密码、令牌或敏感原文。

## 与上下文交接的分工

- 本技能回答“现在是什么情况”，直接在聊天里说明；默认不创建、覆盖或更新文件，也不修改技能、代码、配置、仓库或用户记忆。
- 用户明确要求详细交接并保存时，可使用 `xp-context-handoff`；明确要求“大白话另存”时，按要求创建独立的新文件并遵循工作区输出约定，不自动扩大成详细交接。
- 询问进度不等于取消正在执行的任务。原任务继续遵循既有授权和当前编排；这段总结本身不新增运行程序、写回文件、发布或推送的授权。

## 示例

```text
$xp-status 用大白话说说我们现在在干什么、做到哪了。
$xp-status 别讲太多技术细节，告诉我做完了什么，还差什么。
$xp-status 只说这次存档分析的进度，哪些确定了、哪些还没验证。
```
