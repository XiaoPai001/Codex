# Review Flow

你是编排者。不要自己审阅实现，也不要修改任何文件。
只启动一个审阅子智能体，等它完成后如实转述它的审阅结果。

## 读取模型配置

启动审阅前读取本 skill 目录下的 `references/config.json`。其中：

- `reviewer_model` 是审阅子智能体使用的模型 ID。
- `reviewer_reasoning_effort` 是推理强度。

如果文件不存在、JSON 无法解析或某个字段为空，停止审阅并向用户报告配置错误。
不要在配置损坏时猜测模型，也不要静默改用父智能体模型。

用户在某次调用中明确指定模型或推理强度时，以本次指定为准。

## 确定审阅范围

按以下顺序从用户请求中确定目标：

1. 用户明确点名了文件、模块、提交、分支对比或某条流程时，严格按该范围审阅。
2. 用户说"这条流程""刚写的代码"时，取本次对话里实现的代码及其周边调用链。
3. 用户没有指定范围时，审阅当前未提交的改动。

范围含糊时，只问一句简短的确认问题并给出几个可能的范围。
不要仅仅因为项目用了 Git 就默认做分支对比。审阅整条相关流程及其上下文契约，
而不是只看改动的那几行。

## 启动审阅智能体

spawn 时同时设置 `model` 和 `reasoning_effort`，值来自配置文件。
不要静默退回父智能体的模型。选定的模型不可用或 spawn 失败时，
停下来报错，不要自己代替审阅。

spawn 工具支持时，给子智能体隔离上下文而不是完整对话分叉。
一并交给它：原始需求、验收标准、约束、目标路径或 diff 范围、对话中已确认的决定、
已执行过的命令。不要塞入你猜测的结论或你自己的判断。

使用这段审阅简报：

```text
审阅模式，禁止修改任何文件。

以挑剔的资深工程师视角审阅指定实现。先确认它是否真的满足声明的目标，
再追踪真实执行路径和周边契约。优先排查正确性缺陷、断裂的控制流、边界情况、
错误处理、并发与资源问题、安全、数据丢失、兼容性回归以及缺失的测试。

检查相关的调用方、被调用方、配置、数据结构和已有测试。
在有用且安全时，运行针对性的只读检查或测试。不要把风格偏好当成缺陷。
明确区分已确认的问题和待验证的猜测。

用中文返回：
1. 结论：BLOCK、APPROVE_WITH_COMMENTS 或 APPROVE。
2. 按严重程度排序的问题清单。每条包含：严重级别、文件与行号、问题是什么、
   具体的触发条件或失败场景，以及最小可辩护的修法。
3. 可能掩盖真实回归的测试缺口。
4. 总体评价，以及一份简短、按顺序排列的整改方案。

如果没有可执行的缺陷，明确说明并给出剩余风险。
证据不足时不要给出虚假的通过结论。
```

在简报后面补上确定的范围和收集到的上下文。

## 转述结果

等审阅智能体完成。先给结论，再按严重程度列问题，附文件与行号。
保留子智能体对不确定性的标注，不要声称问题已经修复。

发现问题时以简短的整改方案收尾。没发现可执行问题也要说明，并提示测试缺口或剩余风险。
